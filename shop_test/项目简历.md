# ShopXO 商城接口自动化测试框架

基于 **Python + requests + pytest** 的接口自动化测试项目，对 ShopXO 商城登录接口做自动化测试，涵盖请求封装、日志、数据驱动、断言、测试报告等接口测试核心环节。

## 技术栈

- **语言/框架**：Python 3、pytest、pytest-parametrize
- **接口请求**：requests（HTTP GET/POST 封装）
- **数据驱动**：yaml 测试数据 + pytest 参数化
- **日志**：logging + RotatingFileHandler（日志轮转）
- **测试报告**：Allure（支持一键生成中文版报告）

## 项目亮点

1. **请求统一封装**：封装 `Request` 类，统一在请求前后自动记录 URL、入参、状态码、响应内容，避免每个用例重复写日志。
2. **分层断言**：接口用例按「HTTP 状态码 → 业务返回码 code → 返回字段结构」三层断言，既能定位是网络问题还是业务错误。
3. **数据驱动**：测试数据放在 yaml 文件里，通过 `@pytest.mark.parametrize` 自动为每条数据生成用例，新增测试场景只改数据不改代码。
4. **日志轮转**：用 `RotatingFileHandler` 实现日志按 1MB 自动切分、保留 3 份，方便问题回溯。
5. **中文测试报告**：编写脚本一键生成汉化版 Allure 报告，测试结果直观可读。

## 面试准备：接口测试高频问题

### 1. 简单介绍这个项目
**答：** 我用 Python + requests + pytest 写了一个接口自动化测试框架，测的是 ShopXO 商城的登录接口。测试数据放在 yaml 文件里，用 pytest 参数化自动生成用例，覆盖了登录成功、密码错误、账号不存在、账号为空四种场景。断言分三层：先看 HTTP 状态码，再看业务返回码 code，最后校验返回字段结构。最后用 Allure 生成测试报告。

### 2. 为什么用数据驱动？
**答：** 把测试数据和测试逻辑分开。数据放 yaml 文件，代码只写一次，新增测试场景（比如再加一个「密码长度超限」的用例）只需要在 yaml 里加一条数据，不用改代码。这样好维护，也让用例更清晰。

### 3. 你的断言分几层？为什么？
**答：** 分三层。第一层看 HTTP 状态码是不是 200，判断接口通不通；第二层看业务返回码 code，判断业务逻辑对不对（比如密码错误返回 -4）；第三层校验返回的 data 字段结构是否符合预期。这样分层的好处是：出了问题能快速判断是网络问题、还是业务逻辑问题、还是返回结构不对。

### 4. 接口测试和 UI 测试有什么区别？
**答：** 接口测试直接调后端接口，不经过页面，速度快、稳定、能更早发现问题；UI 测试是模拟真人操作页面，更接近用户真实使用，但慢、容易受页面改动影响。一般是接口测试做核心逻辑回归，UI 测试做关键流程冒烟，两者互补。

### 5. 如果接口返回不是 JSON（比如返回了 HTML）怎么办？
**答：** 我实际遇到过：ShopXO 的 AJAX 接口必须带 `X-Requested-With: XMLHttpRequest` 这个请求头，否则会返回一段 HTML 错误页而不是 JSON。所以我在 config 里统一配了这个请求头。这提醒我：遇到返回格式不对，先检查请求头、Content-Type 这些参数对不对。
